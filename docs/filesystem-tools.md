# Local files for little guys

Bonfire has native file tools wired into its existing agent loop. They run locally and require no hosted API, Docker container, or separate agent runtime.

The command tool also manages persistent apps: `mode=start` returns a stable process ID; `mode=status` checks running state and logs; `mode=stop` stops the managed process tree. `path` defaults to the assigned root. Records/logs live on D: by default and survive backend restarts. Older unmanaged `nohup` launches still require native process inspection. See [shared harness design and results](harness-improvements-2026-10-02.md).

## Set up

1. Open **Tools & connectors → Local folders**. Add a name and an existing absolute folder path, such as `D:\Projects\notes`.
2. Edit or create a little guy. Expand **Local files** and select the tools, or select the whole group.
3. In **Assigned folders**, select the folders it should use and choose **Read only** or **Read & write** for each. Save.
4. Start that guy's chat. Try: “Read my project notes, create a short summary in summary.md, and tell me which file you changed.”

Adding a folder alone grants no little guy access. Existing guys and plain Bonfire chats receive no new file tools automatically. Folder IDs are generated by Bonfire; the model discovers them with `files__list_folders`. Removing a folder in settings revokes the assignment; it does not remove files from disk.

## Tools

| Tool | Behavior |
| --- | --- |
| `files__list_folders` | Discover assigned folders and access modes. |
| `files__list_directory` | List entries with an offset cursor. |
| `files__read_file` | Read raw text pages, separate line ranges, full-file SHA256, and next-line cursor. |
| `files__search_files` | Find filenames recursively by substring; skip links, `.git`, `node_modules` and `vendor`. |
| `files__write_file` | Create or replace a UTF-8 text file; existing files require a current hash. |
| `files__edit_file` | Apply exact text replacements that each match once, preserving CRLF in edits. |
| `files__create_directory` | Create folders and missing parents. |
| `files__restore_file` | Restore a previous file version using its backup ID and the current file hash. |
| `files__run_command` | Run Bash in a writable assigned folder; return exit code, bounded output and timeout status. |

Text files are limited to 2 MB. Read pages and directory listings fit Bonfire's bounded tool output. Filename search stops at 3,000 scanned entries, 100 matches, or its output budget, and reports truncation. Narrow searches by directory when needed. Individual lines too large for a read page produce a clear error. Binary and invalid UTF-8 files are rejected. Writes accept up to 64,000 characters per call; exact-edit replacements accept up to 16,000 characters each.

## Writes and recovery

The model reads before modifying an existing file and submits its SHA256 as `expected_hash`. A mismatch returns an error so it can reread instead of silently overwriting a changed version. Exact edits reject missing or ambiguous text. Bonfire serializes its file operations and checks the file again just before writing.

Before a changed file is written, Bonfire saves its previous text in a UUID-named JSON snapshot. On Windows the default location is **D:\Projects\bonfire-file-backups**, keeping these off C:. Override it with `BONFIRE_FILES_BACKUP_DIR` in the backend environment and restart. Snapshots are local text files and can contain private document contents; they are retained until you remove them. Failed or cancelled writes can leave an unused snapshot.

Successful writes return a verified file hash and `backup_id`. Ask the guy to restore that ID to restore the previous contents; restoration requires a current read/hash and itself creates a new snapshot. Snapshots for newly created files have no previous contents, so restoration does not delete those files. Directory creation has no undo operation.

Chats with filesystem tools allow up to 16 model turns and 20 tool calls for discovery, edits, verification and recovery. Other chats retain the 8-turn/10-call limits. Tool output and model context limits still apply.

Changes within assigned writable folders run immediately without per-write confirmation. Folder boundaries are application checks, not an operating-system sandbox: links/junctions below a root, path escapes and Windows alternate data streams are rejected. External programs can still change files in the small interval between the final check and the write. The file tools do not provide deletion/moves or arbitrary binary editing.

## Bash commands

Assign `files__run_command` explicitly to let a guy run commands. On Windows it uses installed Git Bash; override the executable with `BONFIRE_BASH_PATH`. No WSL or Docker is required. Commands run from an assigned **writable** folder, with a default 30-second timeout (up to 60 seconds), bounded combined stdout/stderr, and a nonzero exit or timeout reported as a tool error. Foreground command trees are stopped on timeout on Windows. Background servers must redirect stdout/stderr; they can outlive the tool call and require separate shutdown.

Shell commands run under your OS account, **not inside a folder sandbox**. They can access paths beyond the assigned working directory and shell changes do not get the file tools' automatic snapshots. The child inherits OS environment essentials rather than Bonfire's backend API keys. Existing guys are not given the command tool automatically. Use native write/edit tools for changes you want backed up.

## Open-source foundation

Bonfire directly reuses `writeFileContent` from the official MIT-licensed [MCP filesystem server](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem), pinned to **2026.8.31**. The [upstream implementation](https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/lib.ts) uses exclusive creation for new files and a temporary file followed by rename when replacing existing files. Bonfire imports the published `dist/lib.js` helper, so dependency upgrades should recheck this internal export. The package's full MCP server is not started; Bonfire supplies its own folder assignments, schemas, paging, exact edits, hash checks and snapshots.

[Oh-my-pi](https://github.com/can1357/oh-my-pi) was also considered. Its content-hash edit anchors are a useful reliability idea, but its full harness includes a much larger runtime and native components. Bonfire uses whole-file SHA256 checks and exact replacements; it does not implement oh-my-pi's Hashline format or invoke its agent.
